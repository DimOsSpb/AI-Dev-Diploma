Блок 5.1 — Эмбеддинги и семантический
поиск
Что делаем
Открываем модуль 5 — закладываем фундамент дипломного RAG-ассистента (чекпоинт 5).
На этом занятии выбирается embedding-модель под предметную область диплома,
обосновывается выбор по языку / размерности / стоимости, считается стоимость индексации
50+ документов и пишется переиспользуемый сервис app/services/embeddings.py с
батчингом и кешем.
Главное инженерное решение этого ДЗ — обоснованный выбор модели.
Задачи
Подготовить mini-benchmark из 5–10 пар в формате (query, relevant_doc,
irrelevant_doc) из предметной области. Это не «погода vs возврат» — это реальные
формулировки пользователей и реальные куски документов проекта. Сохранить в tests/
eval/mini_benchmark.json Структура:
Реализовать модуль app/services/embeddings.py с публичным интерфейсом:
Внутри обязательно: батчинг (минимум 32, рекомендуется 100–512 для OpenAI; для
sentence-transformers на CPU — 16–32), учесть возможные сетевые проблемы.
Возвращаемые векторы должны быть нормализованы — для OpenAI это уже так, для
sentence-transformers явно передавать normalize_embeddings=True . Если модель из E5-
семейства — реализовать два отдельных публичных метода embed_query(text) и
embed_documents(texts) , которые добавляют префиксы query: и passage:
соответственно (см. слайд «Asymmetric vs symmetric embeddings»).
1.
[
{
"query": "...",
"relevant": "...",
"irrelevant": "..."
}
]
2.
def embed_texts(texts: list[str]) -> list[list[float]]: ...

Критерии самопроверки
tests/eval/mini_benchmark.json содержит 5–10 пар вида (query, relevant,
irrelevant) из предметной области диплома.
Повторный вызов embed_texts(["тот же текст"]) в одном процессе или после
рестарта не делает запрос в API (для cloud-моделей — отлавливается отсутствием
новых строк в логе провайдера или счётчиком вызовов; для self-hosted — измеримо
короче latency). Это подтверждается вторым прогоном CLI с замером времени.
При смене модели в .env (например, text-embedding-3-small → text-embedding-3-
large ).
Если выбрана E5-модель — в коде есть отдельные embed_query и embed_documents с
префиксами query: / passage: ; smoke-тест показывает, что без префикса score между
релевантной парой заметно падает.

Теперь у меня есть полная картина. Тема диплома — ИИ-ассистент для мониторинга ИТ-инфраструктуры (Proxmox, Kubernetes, Linux). Это значит что бенчмарк должен содержать вопросы про кластеры, ноды, поды, контейнеры, сеть и т.д.

**ПЛАН:**

1. **tests/eval/mini_benchmark.json** — 5–10 пар (query, relevant, irrelevant) из предметной области:
   - вопросы про Kubernetes (поды, ноды, сеть), Proxmox (контейнеры, VM), Linux (сервисы, логирование)

2. **app/services/embeddings.py** — модуль с:
   - выбор модели (обоснование + реф. ссылка)
   - `embed_texts(texts: list[str]) -> list[list[float]]`
   - батчинг (≥32)
   - кеш (diskcache)
   - retry (tenacity)
   - нормализация
   - для E5: `embed_query(text)` + `embed_documents(texts)` с префиксами

3. **tests/** — smoke-тесты:
   - кэш (повторный вызов не делает запрос API)
   - батчинг
   - E5 префиксы (если выбрано)
   - CLI для замеров latency

4. **.env** — переменные для модели (provider, model_name)

5. **docs/** — обоснование выбора модели (сравнение, стоимость 50+ документов)
