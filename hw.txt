ДЗ — Мультимодальность и streaming
Расширить связку бот+chat-сервис: бот принимает фото, голос и PDF/DOCX и проксирует в
backend; backend конвертирует медиа в content-part (картинка — image_url напрямую в
chat.completions , голос — через Whisper-1 в текстовую расшифровку, PDF/DOCX —
extraction). Streaming через нативный sendMessageDraft (Bot API 10.0). Дополнительно:
обратный канал backend → bot через /notify для проактивных уведомлений.
Что реализовать
Backend: миграция endpoint /messages на multipart (из Б4.1)
Endpoint Б4.1 POST /chats/{chat_id}/messages мигрирует с JSON-body на multipart/
form-data . URL не меняется, контракт расширяется: добавляется опциональное поле
media . Отдельный endpoint /messages/with-media НЕ создаётся — это шум в API.
Новая сигнатура в app/chat/routes.py :
Body: multipart/form-data с полями content: str (Form) и media: UploadFile |
None (File, опционально)
Response: тот же SSE-поток ( data: {"type":"token","delta":"..."} и data:
{"type":"done"} )
Если media is None — отрабатывает обычный текстовый pipeline (как было в Б4.1)
Если media is not None — диспатч по MIME (см. ниже)
Backend: MIME-dispatch в content-part ( app/chat/media.py )
Функция media_to_part(media: UploadFile) -> dict возвращает готовый content-part для
OpenAI Chat Completions API. Картинка — image_url -part напрямую; голос — через
Whisper-1 в text -part; PDF/DOCX — через парсер в text -part. Никакого FFmpeg.

В ChatService.send_message :
К user-message прикладывается [text-part из content, media-part] (если media
есть)
Вызывается один chat.completions.create(model="gpt-5.2", messages=messages,
stream=True, stream_options={"include_usage": True})
import base64
from io import BytesIO
from fastapi import UploadFile
from openai import AsyncOpenAI
client = AsyncOpenAI()
async def media_to_part(media: UploadFile) -> dict:
mime = media.content_type or ""
data = await media.read()
if mime.startswith("image/"):
b64 = base64.b64encode(data).decode()
return {"type": "image_url",
"image_url": {"url": f"data:{mime};base64,{b64}"}}
if mime.startswith("audio/") or mime == "application/ogg":
transcript = await whisper_transcribe(data, media.filename or
"audio.ogg")
return {"type": "text",
"text": f"[пользователь сказал голосом]:\n{transcript}"}
if mime == "application/pdf":
return {"type": "text",
"text": f"[документ PDF]:\n{extract_pdf_text(data)[:30_000]}"}
if mime.endswith("wordprocessingml.document"):
return {"type": "text",
"text": f"[документ DOCX]:\n{extract_docx_text(data)
[:30_000]}"}
raise ValueError(f"Unsupported media type: {mime}")
async def whisper_transcribe(audio_bytes: bytes, filename: str) -> str:
"""Whisper-1 принимает ogg/m4a/mp3/wav/flac/webm напрямую."""
f = BytesIO(audio_bytes)
f.name = filename # SDK берёт расширение для определения формата
result = await client.audio.transcriptions.create(
model="whisper-1", file=f,
)
return result.text

Для image: multimodal LLM видит исходный пиксель
Для audio: основной chat видит уже расшифровку от Whisper (две LLM-операции на
сообщение: STT + chat)
Для PDF/DOCX в text -части — извлечённый текст с обрезкой 30 000 симв
Почему голос идёт через Whisper, а не как input_audio -part: OpenAI chat.completions
input_audio принимает только wav/mp3 у gpt-*-audio , а Telegram присылает ogg/opus.
Whisper-1 формат-агностичен (ogg/m4a/mp3/wav/flac/webm) и дешевле audio-input по токенам
на коротких голосовухах.
Сохранение в ChatMessage :
При сборке messages для следующего LLM-вызова ChatService восстанавливает
мультимодальный content из media_refs.part . Это позволяет LLM «всмотреться» в
исходное фото на следующих репликах.
Минимум один тип медиа обязателен (фото или голос или PDF/DOCX). На максимум — все
три. Парсеры extract_pdf_text / extract_docx_text живут рядом в app/chat/media.py :
PDF: pypdf.PdfReader , max_pages=50 , скан определяется эвристикой (< 100 симв на 5+
страниц)
DOCX: python-docx , обходим параграфы и таблицы

Handlers медиа ( bot/handlers/media.py )
Handler на F.photo → выбирается размер ≤ 2 МБ → скачивается через bot.get_file()
+ bot.download_file(destination=BytesIO()) → backend.send_message(...,
media=bytes, mime="image/jpeg")
Handler на F.voice → скачивается .ogg → backend.send_message(..., media=bytes,
mime="audio/ogg") — конвертация на стороне backend не нужна, Whisper-1 принимает
ogg напрямую
Handler на F.audio (опционально) → скачивается mp3/m4a →
backend.send_message(..., media=bytes, mime=doc.mime_type)
Handler на F.document (с фильтром doc.file_name.lower().endswith((".pdf",
".docx")) и doc.file_size <= 10 * 1024 * 1024 ) → скачивается →
backend.send_message(..., media=bytes, mime=doc.mime_type)
Текстовый handler из Б4.2 теперь вызывает backend.send_message(chat_id,
message.text) без media
Streaming через sendMessageDraft
Заменяется в handle_text (из Б4.2) старый подход ( message.edit_text(buffer) или
плейсхолдер) на нативный streaming:
# bot/services/backend_client.py
async def send_message(
self, chat_id: str, content: str,
media: bytes | None = None, mime: str | None = None,
) -> AsyncIterator[str]:
files = {"media": ("file.bin", media, mime)} if media else None
data = {"content": content}
async with self.http.stream(
"POST", f"/chats/{chat_id}/messages",
data=data, files=files, timeout=120.0,
) as r:
r.raise_for_status()
async for line in r.aiter_lines():
if not line.startswith("data: "):
continue
payload = json.loads(line.removeprefix("data: "))
if payload["type"] == "token":
yield payload["delta"]
elif payload["type"] == "done":
return

Используется bot.send_chat_action(ChatAction.TYPING) пока ждём первый токен. Один
draft_id на весь стрим — Telegram «склеивает» вызовы в один черновик с плавной
анимацией. Финальный send_message фиксирует ответ, иначе черновик исчезнет через ~30
сек.
Backend → Bot: обратный канал /notify
Бот выставляет внутренний HTTP-endpoint, который backend дёргает для проактивных
уведомлений (статус заявки изменился, долгая фоновая задача завершилась, истекает
подписка). Сценарии — из домена дипломного проекта: техподдержка SaaS, HR/онбординг,
e-commerce.
В bot/web.py :
import uuid
from aiogram.types import Message
async def stream_to_chat(message: Message, tokens) -> str:
draft_id = uuid.uuid4().int & 0xFFFFFFFF
buffer = ""
await message.bot.send_message_draft(
chat_id=message.chat.id, text="", draft_id=draft_id,
)
async for delta in tokens:
buffer += delta
if buffer.strip():
await message.bot.send_message_draft(
chat_id=message.chat.id, text=buffer, draft_id=draft_id,
)
if buffer:
await message.bot.send_message(
chat_id=message.chat.id, text=buffer,
)
return buffer

В backend ( app/services/notifier.py ):
from fastapi import FastAPI, Header, HTTPException
from pydantic import BaseModel
from aiogram import Bot
class NotifyRequest(BaseModel):
chat_id: int
text: str
def build_api(bot: Bot, internal_token: str) -> FastAPI:
api = FastAPI()
@api.post("/notify")
async def notify(
req: NotifyRequest,
x_internal_token: str = Header(...),
) -> dict:
if x_internal_token != internal_token:
raise HTTPException(status_code=401)
await bot.send_message(chat_id=req.chat_id, text=req.text)
return {"ok": True}
return api

log_level="info")
server = uvicorn.Server(config)
await asyncio.gather(dp.start_polling(bot), server.serve())

httpx устойчивость
В bot/services/backend_client.py :
Конфигурация httpx.Timeout(connect=3.0, read=60.0, write=10.0, pool=5.0) ; для
streaming-запросов read=120.0 override
Singleton httpx.AsyncClient на всё приложение, создаётся в bot/__main__.py ,
закрывается через await http.aclose() в finally
Retry через tenacity или ручной цикл — только на сетевые errors
( httpx.ConnectError , httpx.ConnectTimeout ), не на 4xx и не на 5xx (5xx может стоить
денег за LLM)
Streaming-запрос, который уже частично отдал данные, не ретраится
Обработка httpx.ConnectError , httpx.ReadTimeout , httpx.HTTPStatusError →
понятные сообщения пользователю (не трейсбек):
ConnectError → «Сервис недоступен, попробуйте позже»
ReadTimeout → «Ответ занимает слишком долго»
HTTPStatusError 429 → «Слишком много запросов, подождите минуту»
HTTPStatusError 5xx → «Внутренняя ошибка сервиса»
import httpx
from app.core.config import settings
async def notify_user(chat_id_tg: int, text: str) -> None:
async with httpx.AsyncClient(timeout=5.0) as c:
r = await c.post(
f"{settings.bot_url}/notify",
json={"chat_id": chat_id_tg, "text": text},
headers={"X-Internal-Token": settings.internal_token},
)
r.raise_for_status()

Критерии «принято»
Endpoint POST /chats/{id}/messages принимает multipart/form-data с content
(обязательно) и media (опционально); отдельного /messages/with-media нет
app/chat/media.py::media_to_part возвращает {"type": "image_url", ...} для
image/*, {"type": "text", ...} для голоса (через Whisper) и для PDF/DOCX
Картинка попадает в основной chat.completions.create напрямую — отдельного
Vision-вызова с возвратом текста НЕТ
Голос проходит через whisper-1 без конвертации (ogg/m4a/mp3 принимаются Whisper
напрямую); subprocess /FFmpeg в backend НЕТ
media_refs.part сохраняется в ChatMessage для повторного использования в
последующих LLM-вызовах того же чата
Минимум один тип медиа работает end-to-end: фото или голос или PDF/DOCX
Бот не импортирует openai , pypdf , python-docx ; обработка медиа живёт в backend,
не в боте
Все вызовы из бота в backend идут через один метод
BackendClient.send_message(chat_id, content, media=None, mime=None)

Бот выставляет /notify endpoint; вызов curl -X POST localhost:9000/notify -H 'X-
Internal-Token: ...' -H 'Content-Type: application/json' -d '{"chat_id":
<tg_id>, "text": "..."}' шлёт сообщение в Telegram
/notify отдаёт 401 без правильного X-Internal-Token
Streaming через draft виден на длинных ответах: черновик плавно растёт до финального
send_message
httpx.AsyncClient — singleton, закрывается в finally
Обработка ошибок backend → текстовые сообщения пользователю, не трейсбек
Один из тестов проверяет SSE-парсинг через httpx.MockTransport
