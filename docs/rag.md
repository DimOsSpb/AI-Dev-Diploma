# Решение по коллекции

Для блока 5.3 создана отдельная коллекция Qdrant:

```
rag_block_03
```

Причина:

Коллекция из блока 5.2 заполнялась напрямую через `qdrant-client` и содержит плоский payload. LlamaIndex сохраняет документы в собственном формате (`_node_content`), который необходим для корректной работы `source_nodes`, цитирования источников и восстановления метаданных.

Поэтому для LlamaIndex используется отдельная коллекция, индексируемая непосредственно через `VectorStoreIndex`.

# Сравнение реализаций

Если исходить **из нашей реализации**, то таблица получится примерно такой.

| Критерий                                                | LlamaIndex                                                                                   | Bare-metal                                                                                  |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **Строк кода (ingestion + query, без импортов)**        | ~80–100                                                                                      | ~220–280                                                                                    |
| **Поддержка форматов из коробки**                       | Markdown, PDF, DOCX, TXT, HTML и десятки других через Readers                                | Только то, что реализовано вручную (в дипломе — Markdown)                                   |
| **Что дописать для PDF/DOCX**                           | Практически ничего — использовать `SimpleDirectoryReader` или соответствующий Reader         | Парсер PDF (`pypdf`), DOCX (`python-docx`), извлечение текста, метаданных, обработку ошибок |
| **Что дописать для batch-ingestion / async**            | Практически ничего — поддержка уже предусмотрена в экосистеме LlamaIndex                     | Самостоятельно реализовать batching, async-загрузку, обработку очередей, контроль прогресса |
| **Где удобнее дебажить top_score / source_nodes**       | Bare-metal удобнее: полностью видны запрос к Qdrant, score и payload                         | Полный контроль над каждым этапом поиска, легко выводить score, payload и retrieved chunks  |
| **Где гибче подменять компоненты (re-ranker, chunker)** | Намного удобнее — chunker, retriever, reranker, postprocessors меняются несколькими строками | Любую замену приходится реализовывать самостоятельно                                        |

### Вывод

В дипломной работе остаётся **реализация на LlamaIndex**. Она обеспечивает значительно более высокий уровень абстракции и позволяет сосредоточиться на бизнес-логике RAG, а не на реализации инфраструктурных компонентов. При этом собственная реализация Bare-metal остаётся полезной для понимания внутреннего устройства Retrieval Augmented Generation, а также значительно упрощает отладку процесса поиска, поскольку даёт полный контроль над каждым этапом формирования эмбеддингов, поиска в Qdrant и построения контекста. Именно поэтому в дипломе используются обе реализации: Bare-metal — как учебная и отладочная, LlamaIndex — как основная промышленная версия.
