Блок 5.2 — Векторные базы данных
Что делаем
Продолжаем дипломный проект: эмбеддинги, выбранные на ДЗ Б5.1, теперь нужно куда-то
положить, чтобы искать в них с фильтрацией и ответом за миллисекунды. На этом занятии
Qdrant добавляется сервисом в существующий docker-compose.yml (рядом с app + redis
+ postgres + bot из чекпоинта 4), создаётся коллекция documents с правильной
размерностью под выбранную на Б5.1 модель эмбеддингов, заливаются 100+ документов с
осмысленным payload и реализуется поиск с фильтрами. На выходе — модуль app/
services/vector_store.py с async-методами, который на блоке 5.3 подключится через
LlamaIndex QdrantVectorStore к этой же коллекции.
Задачи
Qdrant в docker-compose.yml . Добавить сервис qdrant к существующему compose
(продолжение чекпоинта 4 + ДЗ Б5.1). Образ — qdrant/qdrant:v1.14.0 (или новее в той
же мажорной), порт 6333 наружу для дашборда, 6334 для gRPC, named volume
qdrant_storage:/qdrant/storage (без него после docker compose down -v всё
пропадёт), healthcheck по TCP на 6333, restart: unless-stopped .
QDRANT__SERVICE__API_KEY пробрасывается из .env (даже на dev — копируется в
production и забывается). В depends_on сервиса app добавляется qdrant:
{ condition: service_healthy } .
Подключение клиента и конфиг. В app/config.py (Pydantic Settings) добавляются
QDRANT_URL , QDRANT_API_KEY (Optional), QDRANT_COLLECTION (дефолт documents ),
EMBEDDING_DIM (число — берётся из модели, выбранной на Б5.1: 1536 для text-
embedding-3-small , 384 для all-MiniLM-L6-v2 и т. д.). В .env.example прописываются
все четыре. URL и размерность не хардкодятся в коде модуля.
Скрипт scripts/load_to_qdrant.py . Идемпотентный — повторный запуск не должен
дублировать точки. Шаги:
Создаёт коллекцию documents , если её нет:
vectors_config=VectorParams(size=settings.EMBEDDING_DIM,
distance=Distance.COSINE) . Если уже есть — проверяет, что размерность совпадает,
иначе падает с понятной ошибкой (а не молча заливает мусор).
Создаёт payload_index для полей, по которым ведётся фильтрация: минимум
source (KEYWORD), created_at (DATETIME) и одно специфичное полю под
предметку ( tenant_id , department , category , author , access_level — что
осмысленно для конкретного диплома).

Читает 100+ документов из data/ (продолжение коллекции из ДЗ Б5.1 — не «5 строк
лорема», а реальные данные предметной области: фрагменты из PDF/MD/HTML, FAQ,
статьи). На каждый документ — id (детерминированный, например
uuid5(NAMESPACE, source + chunk_index) — ключ к идемпотентности), вектор (через
клиент Б5.1) и payload минимум из 4 полей: source , text (сам чанк, чтобы
возвращать в LLM), created_at , плюс предметное поле.
upsert батчами по 128–256 точек, wait=True на последнем батче — чтобы можно
было сразу искать. В консоль — tqdm -прогрессбар и финальная строка с
points_count из client.get_collection(...) .
Модуль app/services/vector_store.py . Тонкая обёртка над AsyncQdrantClient ,
чтобы остальной код не знал про qdrant-client напрямую (на Б5.3 заменяется на
LlamaIndex — интерфейс не должен поменяться). Методы:
async def upsert(self, points: list[PointStruct]) -> None — батчами, размер
из аргумента (дефолт 256).
async def search(self, query_vector: list[float], top_k: int = 5,
query_filter: Filter | None = None) -> list[ScoredPoint] — через
client.query_points(...) , возвращает list[ScoredPoint] (не голый dict).
async def ensure_collection(self) -> None — создаёт коллекцию + payload-
индексы, вызывается в lifespan FastAPI.
Клиент создаётся один раз ( AsyncQdrantClient(url=..., api_key=...) ), внутри
FastAPI — через DI или модуль-singleton. Новый клиент на каждый вызов не создаётся.
Cosine vs Dot product. На 5 запросах из предметной области (реальные вопросы
пользователя, не «возврат товара» из лекции) сравнивается ранжирование:
Создаются две коллекции — documents_cosine и documents_dot — на одних и тех
же векторах.
Для каждого запроса считается top-5 в обеих, собирается таблица: запрос, top-5 ids в
cosine, top-5 ids в dot, совпало ли ранжирование.
Если эмбеддинги от OpenAI или нормализованных Sentence Transformers —
ранжирование должно совпасть (это sanity check). Если нет — необходимо
разобраться, нормализуются ли векторы; если нет — добавить normalize=True или
преобразование вручную.
Результат и пояснение «почему оставляю COSINE / DOT в production» — в docs/
vector_store.md в раздел «Метрика».
После эксперимента — удалить временную коллекцию ( documents_cosine или
documents_dot ), чтобы не дублировать storage. В проде живёт одна боевая
коллекция; две одинаковые на тех же векторах — учебный артефакт.

Фильтрация по metadata — три примера. Все в docs/vector_store.md с показанным
запросом и top-3 результатами:
Match по строке: один из доступных payload-ключей ( source = "policy_2025.md"
или category = "support" ).
Range по дате: created_at >= today() - 30 days через DatetimeRange(gte=...) .
На примере видно, что выдача меняется: без фильтра — старый документ, с фильтром
— свежий.
Композитный must + must_not: «только тенант X, исключая архивные документы»
(или соответствующий аналог под домен). Это самый частый паттерн в production-
RAG.
(Опционально, +30 минут) pgvector как альтернатива. Если в дипломе уже Postgres
(M3 + M4) — попробовать pgvector 0.8 и halfvec на той же выборке: поднять расширение в
существующий postgres-контейнер ( CREATE EXTENSION vector; ), залить те же 100+
векторов в таблицу documents (id uuid, embedding vector(N), payload jsonb) ,
создать CREATE INDEX ... USING hnsw (embedding vector_cosine_ops) . В docs/
vector_store.md отдельным разделом — числа: latency на 5 одинаковых запросах
(Qdrant vs pgvector), удобство фильтрации (SQL WHERE vs Qdrant Filter ), осознанный
выбор «оставляю Qdrant» / «переезжаю на pgvector». Если заранее известно, что Qdrant
нужен (>1M векторов, hybrid search, sparse) — задачу можно пропустить.
Критерии самопроверки
docker compose up -d qdrant поднимает Qdrant без ошибок, дашборд открывается на
http://localhost:6333/dashboard , docker compose ps показывает Qdrant как
healthy .
python scripts/load_to_qdrant.py загружает 100+ точек за один прогон. Повторный
запуск завершается без дублей: client.get_collection(...).points_count после
второго запуска = после первого.
Размерность коллекции ( info.config.params.vectors.size ) совпадает с
settings.EMBEDDING_DIM . При попытке залить вектор не той размерности скрипт падает
с понятным сообщением, а не молча.
app/services/vector_store.py использует AsyncQdrantClient , не создаёт клиент на
каждый вызов, методы upsert/search/ensure_collection покрыты хотя бы одним
smoke-тестом (pytest или ipython-пример с реальной коллекцией).


В docs/vector_store.md есть таблица «cosine vs dot» с пятью запросами, top-5 id в
каждой колонке и пояснением финального выбора.
В docs/vector_store.md есть три примера фильтров (match, datetime range, must +
must_not) — для каждого показан Python-код фильтра и top-3 результата.
Конфигурация Qdrant — в .env ( QDRANT_URL , QDRANT_API_KEY , QDRANT_COLLECTION ,
EMBEDDING_DIM ); .env.example обновлён, в коде нет хардкода localhost:6333 .
Параметры HNSW либо явно прописаны ( hnsw_config=HnswConfigDiff(m=16,
ef_construct=100) ), либо есть строка-комментарий «оставляю default Qdrant: m=16,
ef_construct=100» с осмысленным обоснованием.

# app/services/vector_store.py — скелет, дорабатывается под проект
from qdrant_client import AsyncQdrantClient
from qdrant_client.models import (
Distance, VectorParams, PointStruct, Filter,
PayloadSchemaType, ScoredPoint,
)
class VectorStore:
def __init__(self, url: str, api_key: str | None, collection: str, dim: int)
-> None:
self.client = AsyncQdrantClient(url=url, api_key=api_key)
self.collection = collection
self.dim = dim
async def ensure_collection(self) -> None:
existing = {c.name for c in (await
self.client.get_collections()).collections}
if self.collection not in existing:
await self.client.create_collection(
collection_name=self.collection,
vectors_config=VectorParams(size=self.dim,
distance=Distance.COSINE),
)
# payload indexes — список под схему проекта

PayloadSchemaType.KEYWORD)

"created_at", PayloadSchemaType.DATETIME)
async def upsert(self, points: list[PointStruct], batch_size: int = 256) ->
None:
for i in range(0, len(points), batch_size):
await self.client.upsert(
collection_name=self.collection,
points=points[i : i + batch_size],
wait=(i + batch_size >= len(points)),
)
