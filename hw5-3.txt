Что делаем
Поверх дипломного сервиса собирается минимальный, но рабочий RAG на LlamaIndex.
После Б5.1 (выбрана embed-модель) и Б5.2 (поднят Qdrant) на руках отдельные кирпичики;
задача — собрать из них целый pipeline и пройти его руками: SimpleDirectoryReader →
SentenceSplitter → QdrantVectorStore → VectorStoreIndex → QueryEngine . Тот же
запрос параллельно реализуется bare-metal (без фреймворка) — чтобы увидеть, что именно
LlamaIndex инкапсулирует, и не воспринимать его как магию.
Инкремент ложится: app/services/rag.py и endpoint, использующий RAG. Сейчас важно
не «сделать хорошо», а прокрутить весь цикл и понять, какой компонент за что
отвечает.
Задачи

1.
Установить зависимости. Ставится бандл-метапакет плюс интеграции, которых в нём
нет:
Бандл llama-index тянет llama-index-core , llama-index-llms-openai и llama-
index-embeddings-openai — для OpenAI отдельно ставить ничего не нужно. Интеграция
с Qdrant и файловые ридеры в бандл не входят. Если в роли эмбеддингов выбран
HuggingFace (обоснование из Б5.1) — добавляется llama-index-embeddings-
huggingface . Версии фиксируются в docs/rag.md .

2.
Подготовить корпус: 10 документов предметной области. В data/rag-block-03/
кладётся 10 файлов ( .md , .txt , .pdf , .docx — что уместно для домена; для PDF/
DOCX нужен llama-index-readers-file ). Можно взять подмножество данных из Б5.2.
Один документ должен быть заведомо не-релевантным теме — он нужен для проверки
fallback-а «не знаю».

3.
Решение по коллекции — записать в docs/rag.md . Коллекция из Б5.2 наполнялась
напрямую через qdrant-client с плоским payload; LlamaIndex хранит ноды в своём
формате ( _node_content ). При подключении к «чужой» коллекции через
from_vector_store метаданные и цитаты source_nodes будут неполными.
Рекомендуется завести отдельную коллекцию (например, rag_block_03 ) и

проиндексировать корпус через LlamaIndex. Фиксируются: размерность векторов,
distance, embed-модель — они должны совпадать с тем, что лежит в коллекции, иначе
retrieval вернёт мусор.

4.
app/services/rag.py — версия на LlamaIndex. Реализуется класс RAGService с
методами build() (индексация/подключение) и answer(question) -> dict . Внутри:
SimpleDirectoryReader(input_dir="data/rag-block-03",
recursive=True).load_data()
SentenceSplitter(chunk_size=512, chunk_overlap=64) (через
Settings.node_parser или явно)
QdrantVectorStore(client=..., collection_name=...) +
StorageContext.from_defaults(vector_store=...)
VectorStoreIndex.from_documents(...) при первой индексации,
VectorStoreIndex.from_vector_store(...) при подключении к готовой коллекции
index.as_query_engine(similarity_top_k=3)
answer() возвращает словарь:
{
"answer": str(response),
"top_score": round(top_score, 3),
"sources": [
{"text": n.text[:300], "source": n.metadata.get("file_name"),
"score": round(n.score, 3)}
for n in response.source_nodes
],
}

Минимум 3 источника в sources . Конфигурация (LLM, embed-модель, chunk_size ,
chunk_overlap , similarity_top_k , имена коллекций) — в .env / app/config.py , не
хардкод.

5.
app/services/rag_baremetal.py — та же логика без LlamaIndex. Повторяется весь
путь руками: чтение файлов → наивный чанкинг → эмбеддинги → upsert в свою
коллекцию с плоским payload → qdrant_client.query_points(...) → сборка промпта
system + контекст + вопрос → openai.chat.completions.create(...) . Старый
client.search(...) — deprecated, используется query_points (как в Б5.2).
Возвращается тот же контракт, что у answer() . Embed-модель и корпус — те же, иначе
сравнивать нечего.

6.
Сравнить две реализации в docs/rag.md . Заполняется таблица:
Критерий LlamaIndex Bare-metal
Строк кода (ingestion + query, без импортов) … …
Поддержка форматов из коробки … …
Что дописать для PDF/DOCX … …
Что дописать для batch-ingestion / async … …
Где удобнее дебажить top_score / source_nodes … …
Где гибче подменять компоненты (re-ranker, chunker) … …

Под таблицей — 3–5 предложений вывода: какая версия остаётся в дипломе и почему

7.
Подключить RAG к FastAPI. Заводится отдельный endpoint POST /rag/query с телом
{"question": "..."} . Отдельный, а не /chat : маршрут /chat в дипломном сервисе
уже занят обычным LLM-ответом из M3. Индекс инициализируется один раз на старте
(через lifespan ), не на каждый запрос. Ответ — JSON с полями answer , top_score ,
sources .
Проверка через Swagger или curl
curl -X POST http://localhost:8000/rag/query \
-H "Content-Type: application/json" \
-d '{"question": "<вопрос по корпусу>"}'

8.
Прогон 5 тестовых вопросов. Подбираются 5 вопросов по своему корпусу:
3 «хороших» — ответ есть в одном из документов, retrieval должен попасть.
1 «средний» — ответ требует синтеза из 2+ документов или сформулирован «не теми
словами», что в тексте.
1 «вне базы» — ответа в корпусе заведомо нет. Должен сработать fallback (модель
сказала «не нашлось» или top_score ниже порога).
В docs/rag.md заводится секция «Прогон 5 вопросов»: для каждого — текст вопроса,
краткий ответ, top-1 source со score, оценка «релевантно / нет» и гипотеза почему
(короткий чанк сломал контекст / не та формулировка / fallback сработал корректно / …)

---
Критерии самопроверки
- app/services/rag.py запускается отдельно ( python -m app.services.rag ) и
возвращает dict с answer + минимум 3 элемента в sources (text, source, score).
- app/services/rag_baremetal.py использует тот же Qdrant и ту же embed-модель,
возвращает совместимый по форме результат.
- docs/rag.md содержит: версии зависимостей, решение по коллекции, таблицу
«LlamaIndex vs bare-metal», прогон 5 вопросов.
- POST /rag/query через Swagger/curl возвращает JSON с answer и sources ; индекс не
пересоздаётся на каждый запрос.
- Конфигурация (LLM, embed-модель, chunk_size , chunk_overlap , similarity_top_k ,
имена коллекций) — в .env / app/config.py , не хардкод.
- Один из 5 вопросов — заведомо вне корпуса, и на нём система не выдумывает: честный
fallback от LLM либо отсечение по top_score .
- В docs/rag.md явно записано: «3 хороших / 1 средний / 1 вне базы», по каждому —
гипотеза
